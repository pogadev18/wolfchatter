# M4 — Devlog and go-live

**Status:** proposed · **Date:** 2026-09-16 · **Branch:** `m4-golive` · **Requirements:** FR-8, and PRD §6 "Delivery"

M4 finishes the product: the AI work log becomes a page, `main` deploys itself to Neon, Render and Netlify, and the repository explains both. It also clears the fixes that M2 and M3 deferred here, because most of them only matter once real traffic, a real proxy and a real database are involved.

## How this plan is verified

M1–M3 were rehearsed task by task in a throwaway clone before the plan was written, so every code block in those plans had been run. **M4 is not rehearsed.** Cloud configuration is one-shot, external and stateful: a scratch repository can only tell us what we already believe, and the dashboards are the only thing that tells the truth. So:

- **Code tasks (T1–T7)** are test-first, in this repository, one subagent per task with a review before the next starts — unchanged from M3, minus the scratch clone.
- **Provider steps (P1–P8)** are executed live, one at a time, in conversation. Each step names *what the user does*, *what is checked before moving on*, and *what breaks if it is wrong*.
- **Anything a provider forces us to learn** (proxy addresses, build quirks, SSL behaviour) becomes a work-log entry the same day, not a note at the end.

Estimated shape: seven code tasks, eight provider steps, three documents. The provider phase is the one that cannot be parallelised — it is a conversation, and it is gated on accounts that only the user can create.

## Decisions

Each decision names the alternative it beat, so a reviewer can disagree with the reasoning rather than guess at it.

**D1 — The devlog is built, not served.** `worklog/*.md` is read at build time by a Vite plugin, validated with `@wolfchatter/worklog`, and emitted as a typed module. *Alternative:* a `GET /api/worklog` endpoint. Rejected: it would put file I/O in an API that otherwise only talks to Postgres, add a contract surface, and make a static page depend on a sleeping free instance. The work log ships with the code, so a build is exactly when it changes.

**D2 — Markdown is rendered at build time, not in the browser.** The plugin turns each entry's body into HTML with `marked` (an exact-pinned devDependency of `apps/web`) and the page inserts it. *Alternative A:* a Markdown parser in the bundle — pays parse cost on every visit for content that never changes. *Alternative B:* `white-space: pre-wrap` and no parser — free, but FR-8 asks for a rendered timeline and the raw entries read as a wall of `##`. The content is our own repository at build time, the same trust level as the app's own source; the insertion point carries a comment saying exactly that.

**D3 — The web app is built in GitHub Actions; Netlify only receives `dist`.** *Alternative:* connect the repository to Netlify and let it build. Rejected for three reasons: the devlog needs full git history and Netlify's clone depth is not ours to control; the deploy must not start before CI is green and the API is live, which Netlify's own trigger cannot express; and one build of one commit is easier to reason about than two builds of the same commit.

**D4 — No deploy previews.** The Netlify site is never linked to the repository, so no preview origins exist. *Alternative:* add `deploy-preview-*.netlify.app` to `CORS_ORIGINS`. Rejected: Netlify cannot proxy WebSockets, so a preview would talk to the production API and the production database from an origin we would have to keep allowlisted by wildcard. Deleting the origin is cheaper than guarding it. `INFRASTRUCTURE.md` records what enabling previews would require.

**D5 — Migrations run in the deploy workflow, before the API deploy.** *Alternative A:* Render's pre-deploy command — not available on free instances (verified in Render's deploy documentation). *Alternative B:* migrate on boot — a free instance boots on every wake-up from sleep, so every cold start would pay for it, and two boots could race. The workflow runs it once, in a place whose logs we already read. The rule this implies is written down in `INFRASTRUCTURE.md`: **migrations must be backward compatible with the version currently running**, because they land before the new code does.

**D6 — Render deploys via a deploy hook, with Auto-Deploy off.** Render's default is to deploy on every push to the linked branch, which would ship code CI has not judged. Off + hook puts the trigger in the workflow, after CI and after migrations. Render's "After CI Checks Pass" setting was considered and rejected: it deploys the API but cannot hold the web deploy until the API is actually serving the new commit.

**D7 — The deploy is verified by polling `GET /api/health` for the commit**, not by trusting the hook's 200. Render answers the hook before the build starts. The poll is a tested Node script in the repository (`apps/api/src/deploy/wait-for-health.ts`), not inline shell, because its retry, timeout and mismatch behaviour is exactly the kind of logic that silently passes when it should fail.

**D8 — The workflow's SHA comes from `github.event.workflow_run.head_sha`.** In a `workflow_run` event `github.sha` is *the default branch's tip*, not the commit whose CI passed. Using it would compare the health commit against the wrong SHA — green when the deploy is stale, red when a second commit lands. The checkout uses the same ref.

**D9 — ~~`deploy.yml` also accepts `workflow_dispatch`, so the pipeline can be rehearsed from `m4-golive` before merging.~~ Wrong, corrected during execution.** `workflow_dispatch` carries the same constraint as `workflow_run`: GitHub only offers the trigger for a workflow file that exists on the **default branch**. D8 identified that trap for the automatic trigger and this decision was written as though the manual one escaped it. It does not, so there is no way to run `deploy.yml` from a feature branch.

`workflow_dispatch` stays in the workflow — it is what re-runs a deploy after the merge without pushing a commit — but it cannot rehearse one. The rehearsal moves to P7 instead, which now runs each step's real command locally, in order, against the real providers: the same migration, the same health poll, the same build, the same publish. What that cannot cover is the YAML plumbing itself — secret wiring, checkout, SHA resolution — which is first exercised by the automatic run after the merge. P8 therefore becomes a verification step with a rollback, not a formality.

**D10 — Secrets hold values that grant access; variables hold URLs.** Secrets: `DATABASE_URL`, `RENDER_DEPLOY_HOOK_URL`, `NETLIFY_AUTH_TOKEN`. Variables: `API_ORIGIN`, `NETLIFY_SITE_ID`. URLs in the clear make the deploy log readable — which SHA, which origin, which site — and none of them is a credential.

**D11 — `TRUST_PROXY` is derived from a live request and proven against a spoofed header.** Render puts Cloudflare and its own load balancers in front of a service, so the socket address is a proxy and `X-Forwarded-For` is the only source of a client address. A guess here is not neutral: too permissive lets any client forge its address and defeat the rate limit; too restrictive puts every visitor in one bucket. The probe is `POST /api/rooms` with an invalid body — it counts against the limit before validation and writes nothing — read back through the `x-ratelimit-remaining` header. No diagnostic endpoint, no junk rows in production.

**D12 — Scope.** In: every deferred finding from the M2 and M3 reviews that the user listed. Out, and left to M5: services throwing HTTP-shaped `ApiError`s against PRD §2, and everything the M3 review explicitly accepted as-is.

### T1 — The work log as build-time data

**Goal.** `worklog/*.md` becomes a validated, typed, commit-annotated array the web app can import, and the work-log `date` field finally requires whole seconds.

**Changes.**
- `packages/worklog/src/schema.ts`: `date: z.iso.datetime({ precision: 0 })`.
- `packages/worklog/src/history.ts` (new): `parseAddedCommits(gitLog: string): Map<string, string>` — parses `git log --diff-filter=A --format=%H --name-only -- worklog` into file name → the commit that added it. Pure.
- `packages/worklog/src/devlog.ts` (new): `buildDevlogEntries(files, commits, renderBody): DevlogEntry[]` — validates through the existing `validateWorklog`, attaches `commit: string | null` and the rendered `html`, newest first. Pure; the Markdown renderer is injected so the test does not depend on `marked`.
- `apps/web/plugins/worklog.ts` (new): the Vite plugin. Reads the directory, shells out to `git`, calls the two pure functions, serves `virtual:worklog`. Thin by design — everything worth asserting lives in the two functions above. Outside `apps/web/src`, so `node:*` imports are allowed by `biome.json`'s override.
- `apps/web/src/virtual-worklog.d.ts`: declares the module as `DevlogEntry[]`, imported **type-only** so nothing from `packages/worklog` reaches the bundle.
- `apps/web/package.json`: `marked` and `@wolfchatter/worklog` as exact devDependencies.

**Test-first.**
1. `schema.test.ts`: a date with fractional seconds (`2026-09-16T04:17:00.500Z`) is rejected; whole seconds pass. Watch it fail on the current schema.
2. `history.test.ts`: a `git log` fixture with two commits and three files maps each file to its adding commit; a file with no add event is absent; output from a shallow clone (no add events) yields an empty map rather than throwing.
3. `devlog.test.ts`: entries come back newest first; an invalid file makes it throw with the file name in the message; a file with no commit gets `commit: null`; the body is passed through the injected renderer.
4. Then the plugin, then `pnpm worklog:check` over the real `worklog/` — which must stay green, since every existing entry already uses whole seconds.

**Acceptance.**
- `pnpm test` covers the three units above; `pnpm worklog:check` passes unchanged over the 30-odd existing entries.
- `pnpm --filter @wolfchatter/web build` succeeds and the emitted module contains one object per file in `worklog/`, each with a 40-character `commit` — run in this repository, which has full history.
- With `GIT_DIR` pointed at a shallow clone, or with `git` unavailable, the build still succeeds and every `commit` is `null`. The page must degrade, not fail: CI is where a missing commit gets caught (T6), not a developer's machine.

**Risk.** Entry files are never renamed, so `--diff-filter=A` without `--follow` is correct; a rename would silently drop the commit. The plugin's comment says so.

### T2 — `/devlog` (FR-8)

**Goal.** The timeline itself: every entry, filterable, deep-linkable, with its commit and its related entries.

**Changes.**
- `apps/web/src/main.tsx`: `<Routes>` — `/` renders `App`, `/devlog` renders `Devlog`, anything else redirects to `/`. `useRealtime` stays inside `App`, so **opening `/devlog` opens no socket**.
- `apps/web/src/devlog/` — `devlog-page.tsx`, `entry-card.tsx`, `filters.ts` (pure: given entries and a filter state, return the visible entries and the available options), `filters.test.ts`.
- `apps/web/public/_redirects`: `/*  /index.html  200`, so Netlify serves the SPA on a deep link.

**Constraint discovered at P2, and the reason this file is the only one Netlify gets:** Stadia serves a tile to any request carrying a `Referer` and answers **401 to a request without one** — measured, not assumed. Browsers' default `strict-origin-when-cross-origin` sends the origin and the tiles load. So nothing in this app may ever send `Referrer-Policy: no-referrer`: not a `<meta>` tag, not a `netlify.toml` headers block, not a "hardening" pass. It would 401 every tile and drop FR-1 to the OpenStreetMap fallback, silently, because the fallback is designed to look fine.
- A small `Devlog` link in the chat panel, and a "Back to the map" link on the devlog.

**Behaviour.** Newest first, grouped by day. Each card: time, title, phase and outcome badges (severity too, for issues), agent, task id, the rendered body, a link to the commit on GitHub, and links to `related` entries that scroll to them. Filters for phase, outcome and agent, kept in the URL (`/devlog?phase=api&outcome=issue`) so a filtered view can be shared, with a count and a "no entries match" state.

**Test-first.**
1. `filters.test.ts`: filtering by phase, by outcome, by both; an unknown value in the URL is ignored rather than emptying the page; the option lists come from the entries present.
2. `e2e/devlog.spec.ts`: the page lists every entry newest first; choosing an outcome narrows the list and changes the URL; loading a filtered URL directly applies the filter; **at least one card shows a commit link** (this is the assertion that makes `fetch-depth: 0` real in T6); a related link moves to that entry; `/devlog` opens no WebSocket.

**Acceptance.** `pnpm test` and `pnpm test:e2e` green; the page renders all entries with no console errors; keyboard reachable (filters are real form controls, cards are not focus traps).

### T3 — API hardening for production

**Goal.** The five API findings M2 deferred, all of which only bite under a real proxy, a real pool or a hostile client.

**Changes and their tests.**

| Finding | Change | Test |
|---|---|---|
| Rate limiting counts an IPv6 client's every address separately | **No code needed.** `@fastify/rate-limit` 11.2.0 already defaults to `ipv6Subnet: 64` and already unwraps IPv4-mapped IPv6; the option is pinned explicitly so a library default change cannot move every bucket silently | Regression tests: two addresses in one /64 share a bucket, a third /64 does not, `::ffff:1.2.3.4` shares the IPv4 bucket. Honest about being pins rather than a RED-first cycle |
| A socket may join unlimited rooms | A cap per socket in `socket-server.ts`; over it, `room:join` acks `{ ok: false, error }` | A socket client joins up to the cap, then is refused, and a leave frees a slot |
| `GET /api/rooms` is unbounded | Newest `MAX_ROOMS` (1000) by number, returned oldest-first as before | Three rooms with a limit of two returns the newest two, ascending |
| A slow query holds a connection for ever | `statement_timeout` on the pool in `db/client.ts` | A deliberately slow statement rejects with Postgres' `57014`, and a normal query is unaffected |
| `apps/api/.env` reaches the tests | `test/postgres.ts` resolves the database URL from the real environment, else `.env.example` — never `.env` | A unit test of the resolver against a fixture directory containing both files |
| A deployed database could connect without verifying TLS, silently | `env.ts` requires `sslmode=verify-full` on any `DATABASE_URL` whose host is not loopback; the API refuses to start otherwise | Loopback with no `sslmode` passes (local dev, CI, Playwright are untouched); a hosted host without it is rejected with a message naming the fix; with it, passes |

The last row comes from P3, not from a review: `pg` treats Neon's `sslmode=require` as `verify-full` **today** and will treat it as libpq's unverified `require` after pg v9, so a dependency bump would downgrade production TLS with no error and no failing test. Writing `verify-full` into the three places `DATABASE_URL` is set fixes it; this rule is what stops the next person from leaving it out. See `worklog/2026-09-16T0555-pg-treats-sslmode-require-as-verify-full-until-it-doesn-t.md`.

**Acceptance.** `pnpm test` green; `pnpm check` green; no behaviour change for a single IPv4 client, which is what every existing test asserts.

**Note.** The `GET /api/rooms` bound changes what a client sees once there are more than 1000 rooms: the oldest pins stop being returned. That is a deliberate trade against an unbounded response, it matches "paging older items is out of scope", and it goes in the README's API table.

### T4 — Web resilience

**Goal.** A crash shows something; a hung request stops pretending; a production build reads its own `.env` file.

**Changes.**
- `apps/web/src/app-error-boundary.tsx`: a class boundary around both routes, with a message and a Reload button. Its pure parts — `getDerivedStateFromError` and the fallback's message for a given error — are unit-tested directly. *This is a shallow test and the plan says so:* covering the boundary through a rendered crash would mean adding a component-testing stack (jsdom plus a testing library) that this repository deliberately does not have, which is a larger change than the fix. The work-log entry records the trade.
- `apps/web/src/api/client.ts`: every request carries an abort signal with a timeout (10 s), built by a small `timeoutSignal(ms)` helper so fake timers can drive it. An aborted request is a temporary failure, so the existing retry path already covers it — a hung POST now fails and offers Retry instead of saying "Sending…" for ever.
- `apps/web/vite.config.ts`: `loadEnv(mode, __dirname, 'VITE_')` instead of `process.env`, so `apps/web/.env.production` is visible to the check and a local production build stops failing confusingly. Real environment variables still win, which is what the Playwright web server relies on.

**Test-first.** A fetch that never resolves rejects once the timeout elapses, and the request carries a signal; `isTemporaryFailure` is true for that rejection; the boundary's derived state and message; then a manual check that `pnpm --filter @wolfchatter/web build` succeeds with `VITE_API_URL` in `apps/web/.env.production` and still fails with no value anywhere.

### T6 — CI and the deploy workflow

**Goal.** `main` deploys itself, and CI notices the two things that would make the deploy lie.

**CI (`.github/workflows/ci.yml`).**
- `fetch-depth: 0` on the end-to-end job's checkout, because that job builds the web app and the build resolves work-log commits from history. T2's "a card shows a commit link" assertion is what turns this from a comment into a check.
- A new step in `checks`: run `pnpm db:generate` and fail if `apps/api/drizzle` changed, so a schema edit without a generated migration cannot reach `main`.

**Deploy (`.github/workflows/deploy.yml`, new).** Triggers: `workflow_run` on CI completing on `main`, and `workflow_dispatch`. Guarded by `if: conclusion == 'success'`, serialised by a `deploy` concurrency group, and permissions limited to `contents: read`.

1. Resolve the SHA: `github.event.workflow_run.head_sha`, else `github.sha` for a manual run (D8). Echo it.
2. Checkout that ref with `fetch-depth: 0`; install.
3. `pnpm db:migrate` against `DATABASE_URL` (D5).
4. `POST` the Render deploy hook; fail on a non-2xx.
5. `node apps/api/src/deploy/wait-for-health.ts --url "$API_ORIGIN/api/health" --commit "$SHA"` — polls until `commit` matches, with a timeout that covers a free-tier build and boot (10 minutes), and fails with the last body it saw.
6. Build the web app with `VITE_API_URL=$API_ORIGIN`.
7. Publish to Netlify — ~~`pnpm dlx netlify-cli@<pinned> deploy --prod --no-build --dir dist`~~ **corrected during execution, twice:** the command as written fails under pnpm 12 (`ERR_PNPM_DLX_MULTIPLE_BINS`, `ERR_PNPM_IGNORED_BUILDS`), and a relative `--dir dist` resolves against the repository root rather than the working directory, which the live rehearsal found. What ships is `pnpm dlx --allow-build=esbuild --allow-build=sharp --allow-build=unix-dgram --package=netlify-cli@27.7.0 netlify deploy --prod --no-build --dir "$GITHUB_WORKSPACE/apps/web/dist"`, **with `apps/web` as the working directory** and `NETLIFY_AUTH_TOKEN` plus `NETLIFY_SITE_ID` in the environment; `.github/workflows/deploy.yml` explains each part. Pinned rather than a repository devDependency: the CLI is a large tree that nothing else needs, and CLAUDE.md pins exactly (D10, and the pin is written out in full).

   The working directory is not cosmetic. Run from the workspace root, the CLI detects the four pnpm packages and asks which one to work with; with nothing to answer it crashes (`ERR_USE_AFTER_CLOSE`), which is what happened on a real invocation during P1. Actions has no TTY either. Run from `apps/web` and the question never arises.

**Test-first, for the part that has logic.** `apps/api/src/deploy/wait-for-health.test.ts` with an injected fetch and clock: matching commit resolves; a wrong commit keeps polling and then times out naming both SHAs; a 503 keeps polling; a body that fails `healthResponseSchema` keeps polling; a network error keeps polling; the timeout is enforced. The YAML itself is reviewed, then proven by D9's manual run — the only honest way to test a workflow.

**Acceptance.** `pnpm check` green; the deploy workflow runs end to end from `workflow_dispatch` during P7 and the Netlify site serves the new build.
